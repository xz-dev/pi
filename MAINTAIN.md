# Downstream maintenance

This fork is rebuilt from `earendil-works/pi` rather than developed directly on generated `main`.

## Branch ownership

- `upstream/main` is the rebuild baseline.
- `ci` owns downstream workflows, packaging, release gates, this guide, and the downstream README.
- `patch/contributor-approval` remains the bot-owned approval branch, including preserved commit `fa047a9bc8f3254bfde47bad2e93207f7a8bf62d`. After `ci`, generated `main` applies a deterministic additive union of the current upstream `.github/APPROVED_CONTRIBUTORS` file plus names present only on that branch. Whole-file replacement is forbidden.
- `scoop` is an unrelated-root distribution branch containing only generated `bucket/pi.json`.
- Product changes remain on the ordered `patch/*` branches declared in `.github/workflows/upstream-sync.yml`.
- `patch/single-executable` is one patch based on upstream for the single-file distribution runtime: embedded assets with a lazily materialized `os.tmpdir()/pi-resources-<uid>/<target>/<version>` cache, lock-free `pi update --self` with a `pi-<version>` backup, strict `pi update --clean`, embedded-Bun package operations through `process.execPath`, the `*.managed.lock` channel refusal, and the fork prerelease changelog baseline. It also owns the opt-in update mirror chain (`pi update --mirror`, repeated `--mirror-url` values replacing literal `https://github.com`, `--no-mirror`, save-only `--permanent` into global `updateMirrors`) and the mandatory Sigstore client verification of the release manifest through a bundled pinned public-good trusted root, the `xz-dev/pi` main-branch release-workflow certificate identity, the GitHub OIDC issuer, a GitHub-hosted signer, and the manifest's full source commit. It supersedes the retired `patch/xz-bundle-lifecycle`, `patch/freebsd-launcher`, `patch/use-embedded-bun-package-manager`, `patch/git-package-storage`, `patch/changelog-prerelease`, and `patch/self-update-managed-by`; those branches are retained for history but are not fetched or merged. `ci` owns the raw-executable packaging, release inventory, smoke/E2E, Scoop, README wording, and sync registration.
- Retired: `patch/xz-bundle-lifecycle` was one linear patch for native-wrapper self-update, `pi update --clean`, and bundle usage claims. The claims add process-lifetime shared claims and held exclusive retirement transactions. The native carrier, runtime registration, cleanup/replacement behavior, focused tests, and its target-aware native build helper live on the patch. `ci` owns archive inclusion, required-path inventory, packaged smoke/E2E, README wording, and sync registration. Filesystem classification is warning-only during `pi update --clean`: recognized NFS/SMB/CIFS/Ceph/AFS/NCP/9P emit a warning, generic FUSE is not classified by type, and actual lock outcomes remain authoritative. The safety guarantee requires participating processes to observe one effective lock domain.
- Embedded-Bun package management and Git package storage now live inside `patch/single-executable`. Unknown conflicts stop the replay and must be repaired on the owning patch branch. Official Bun 1.4.2 fixes the Git-dependency npm-lock migration failure. Projectless metadata remains unsupported: embedded default updates print the lookup error and an explicit downgrade-risk warning, then continue when the target version is unknown. Successful version queries retain no-downgrade checks and exact pins remain pinned. Explicit overrides retain their existing policy.
- `patch/freebsd-support` adds FreeBSD platform integration and builds the shared POSIX XCB clipboard source for FreeBSD. The single executable needs no FreeBSD launcher; `patch/freebsd-launcher` is retired. `ci` owns the FreeBSD target and native FreeBSD VM release gate.
- Generated `main` contains one countable squash integration commit for `ci` and each enabled patch. Do not fix release or product problems only on generated `main`.

## Rebuild rules

1. Fetch a specific fresh upstream `main`, `ci`, and every configured patch ref.
2. Rebuild in the fixed order owned by `scripts/rebuild-from-inputs.sh`, which is the single source of truth for the integration sequence. The workflow fetches current refs, resolves each tip once for that run, and invokes the driver with those transient IDs; no commit-ID table is maintained in the repository. The replay runs inside a fresh standalone scratch clone the script creates at `--target` (a path that must not already exist); the source repository's refs, index, files, and linked worktrees are never modified. Current input IDs are recorded automatically in the marker commit for idempotency and auditability.
3. Stop on unexpected conflicts or empty patch integrations.
4. Run all pre-push build, check, focused integration, packed-release, GitHub Release candidate, audit, and signature gates.
5. Update `main` only with `--force-with-lease`; a lease failure requires investigation and a fresh rebuild.

For local diagnosis, run `scripts/rebuild-from-inputs.sh --source <repo> --target <fresh-path>`. The script resolves the current local upstream, ci, and patch refs unless an explicit vector is supplied; it does not fetch network remotes or push. The target must be outside the source, its Git storage, and all linked worktrees. Full runs use every input in `PATCH_ORDER`; supplying only some `--patch` inputs requires `--diagnostic`. Diagnostic subsets and `--stop-before <patch-name>` prefixes always receive non-publishable markers. `--print-inputs` and `--print-marker` show the current resolved vector when given `--source`. The running driver and helper bytes must come from the selected ci checkout. Unknown input names, unresolved refs, incomplete explicit vectors, and merge failures stop the owned scratch run without modifying its source.

Scheduled runs and ordinary `workflow_dispatch` runs always select the current upstream and enabled patch refs. A marker comparison makes an unchanged vector a no-op; a changed ref produces a fresh scratch replay. Fixed-input approval is intentionally not part of the normal sync path.

## Local commits on `ci`

Commit signing is off for this project: `commit.gpgsign=false` is set repository-locally (including each isolated clone/worktree of this repository); do not change global Git signing config. This is unrelated to release Sigstore/OIDC attestation and publication verification, which remain mandatory. Keep the no-auth-bypass rule for actual credentials: never alter Git identity to evade checks.

The pre-commit hook runs repo-wide `npm run check`, including `tsgo`. Provider model data is gitignored and hydrated from a changing catalog, so fixture model IDs can differ from the IDs represented by that data. Generated `main` uses a different upstream baseline; its check result must be measured separately, not inferred from a check in the `ci` checkout.

When an explicitly authorized commit touches `ci`-owned files:

1. Inspect status and stage only the intended files; preserve other sessions' work.
2. Run `npm run check` and retain full output and the actual exit code.
3. If failures are confined to the known stale-model-ID/catalog type mismatch class documented in `AGENTS.md`, the repository policy permits `git commit --no-verify`. Do not edit product fixtures or regenerate catalogs merely to make that hook green.
4. Any other failure must be fixed or reported as a blocker before committing. Do not swap whole product directories to upstream, clean untracked source files, or alter Git identity/signing to bypass a failure.

## README synchronization checklist

Run this checklist whenever a downstream feature, fix, default, command, installation requirement, release target, or patch activation/retirement changes. README updates belong on `ci`, alongside the corresponding integration change.

1. Compare the enabled patch refs in `.github/workflows/upstream-sync.yml` with the root `README.md`. Every user-visible capability must have a current description, a concrete use case, and a link to its persistent patch branch. Internal support patches may be covered by the feature they support; document their dependency/order details here rather than presenting them as separate user features.
2. Update affected installation, update, compatibility, and disabled/removed-patch sections as well as the feature list. A change to defaults or failure handling must state the current behavior and limits, with links to detailed package docs. Updating package docs or this guide alone does not complete the root README update.
3. Verify branch links and technical claims against current source and workflows: target/CPU requirements, package-manager prerequisites, sync order, and blocking versus advisory checks. Remove obsolete compatibility-branch descriptions when integration changes.
4. Before reporting delivery complete, inspect the README at the rebuilt remote `main` SHA and confirm it contains the intended `ci` documentation. Distinguish unpublished documentation changes from descriptions verified in a released artifact. If synchronization or publication has not run, report it as pending.

## GitHub Release distribution rules

- Only an `xz-dev/pi` `refs/heads/main` push or explicit dispatch from `main` may publish. An explicit workflow dispatch from any non-`main` repository branch is a non-publishing release probe that must complete source validation, all 14 builds, archive acceptance, and the aggregated acceptance record while `attest-release-candidate`, both signed-update jobs, and `publish-release` remain skipped: such a run cannot satisfy the main-only signer identity, so the non-publishing probe no longer runs self-update E2E at all. In every context the checked-out clean `HEAD` and `GITHUB_SHA` must be identical.
- `scripts/lib/bun-targets.mjs` is the authoritative 14-target Bun 1.4.2 descriptor matrix. Public baseline/modern x64 asset names remain for update compatibility, but both aliases compile the same Nehalem-compatible runtime-dispatched Bun target. Every Release build runs on the matching OS and architecture, using GitHub-hosted runners or a FreeBSD 14.3 guest of the target architecture, so all fourteen artifacts use `--minify --bytecode --format=esm`; ad-hoc cross-builds omit bytecode because cross-compiled bytecode remains unsafe (oven-sh/bun#18416). `scripts/build-binaries.sh` produces one raw single-file executable per target with all runtime assets embedded. `scripts/prepare-github-release.mjs` wraps each executable in `pi-<target>.zip` (one deflated `pi`/`pi.exe` entry, mode 0755, fixed timestamp, written by `scripts/lib/github-release.mjs` without external tools), records both the ZIP and the inner executable identity in schema-7 `release-manifest.json`, and emits `SHA256SUMS` over the ZIPs, manifest, and notices plus a pre-sign `attestation-subjects.jsonl` filename list covering those files and `SHA256SUMS` itself. The raw executables stay in the CI candidate for smoke and acceptance and are never uploaded. There are no generated installer scripts or hybrid npm tarballs.
- FreeBSD amd64 and arm64 are built and accepted by `scripts/freebsd-release.sh` in the SHA-pinned `vmactions/freebsd-vm` guest on a GitHub-hosted x64 runner with `/dev/kvm`. The amd64 guest is KVM-accelerated. GitHub has no arm64 KVM host, so the arm64 guest runs under QEMU TCG; its descriptor is the only one with `emulated: true`, and its timing budgets (not size budgets) are multiplied by `EMULATED_SMOKE_SLOWDOWN`, calibrated from a measured TCG run. Both ZIPs are built inside the guest of their own architecture and run the same acceptance: bytecode startup, a display-less TUI, native X11 text/image reads, usage claims, and live-session cleanup. Guest evidence reports FreeBSD and the guest architecture rather than the Linux host.
- The manifest freezes the exact tag, full commit, downstream and upstream API versions, per-platform bundle archive metadata (file, bytes, sha256), the bundle layout version, and the required-path inventory per platform. The verifier checks every required path and rejects unknown unsafe archive entries.
- Distribution versions and exact tags are `<api>-xz.<GITHUB_RUN_NUMBER>.<GITHUB_RUN_ATTEMPT>.g<sha8>` and `xz-v<distributionVersion>`. Each workflow attempt has its own immutable tag; repeated execution within that attempt resumes the same tag.
- The publication workflow builds one target per parallel job on a matching native OS and architecture, aggregates exactly 14 archives, proves each final native executable loads its entrypoint from embedded bytecode, runs native smoke on each GitHub-hosted OS/architecture, runs musl targets in pinned native userspaces, and executes the same-version forced-reinstall, negative-proof, and prior-release upgrade legs of the signed self-update E2E before publication. Linux archive smoke must provision an explicit temporary Xvfb display and actually call both `getText()` and `getImage()` on the packaged helper; `undefined` means unavailable and is not an empty clipboard. Never replace calls with presence-only checks. Musl's basic TUI probe remains in the unchanged pinned image without XCB libraries. Its clipboard probe adds only a read-only, SHA-256-pinned Alpine XCB library closure and the temporary X11 socket, still with networking disabled. Aggregation checks the library evidence and the invoked helper's hash against the archive. The musl provenance file records `upstream-prebuilt`, the checked-out source commit, source/header/build-script hashes, helper bytes, and the packaged MIT license; it must not claim a downstream Rust build. `scripts/build-musl-clipboard.sh` now stages that upstream helper without compiling or downloading an addon.
- After the acceptance record, a separate main-only `attest-release-candidate` job receives `contents:read`, `id-token:write`, and `attestations:write`. It re-runs the packaging verifier on the unsigned candidate, creates GitHub build-provenance attestations for the 14 bundles, manifest, acceptance record, notices, and checksum file (18 subjects), verifies the emitted Sigstore bundle against every subject under the pinned main-branch signer identity — including once under an empty `GH_CONFIG_DIR` with `GH_TOKEN`/`GITHUB_TOKEN` unset — then replaces the pre-sign `attestation-subjects.jsonl` filename list with the verified signed JSONL bundle and uploads the result as the `github-release-attested-<sha>` artifact. Native, musl, and FreeBSD self-update gates and `publish-release` consume only that attested artifact.
- Publication is staged as a draft. An interrupted draft may be resumed only when its target commit is exact and its uploaded assets are an exact hash-matching subset; only missing assets are uploaded. No asset is overwritten. A mismatch, unknown asset, wrong commit, or incomplete already-public Release fails closed.
- After all assets and hashes are verified, publish as non-draft and non-prerelease. Re-read `refs/heads/main` immediately before that transition: use `make_latest=true` only when it still equals `GITHUB_SHA`; otherwise publish the immutable historical Release with `make_latest=false` so a delayed older run cannot replace Latest.
- An already-published Release with the exact target and exact complete asset hashes is an idempotent no-op. Releases, tags, and assets are immutable and retained; normal automation never deletes or overwrites them.
- Installation is self-contained: the executable inside `pi-<target>.zip` is the entire product. Its embedded resources (docs, themes, WASM, HTML export templates, examples, the native clipboard helper) are materialized lazily into a per-user tmpdir cache at `os.tmpdir()/pi-resources-<uid>/<target>/<version>`; a nonempty cache directory is reused as-is. Installations up to `xz-v1.0.0-xz.253` (raw-executable releases) and the older ZIP-bundle layout (`pi` wrapper + `pi-native` + loose assets) cannot self-update onto schema-7 ZIP releases; users reinstall once from the current ZIP.
- `pi update --self` from an xz-dev binary discovers only the latest immutable `xz-dev/pi` Release through the ordered mirror chain (direct GitHub unless `--mirror`, `--mirror-url`, or a saved `updateMirrors` setting chooses otherwise; `--no-mirror` forces direct for that invocation), authenticates `release-manifest.json` with the bundled Sigstore trusted root against the main-branch `publish-github-release.yml` certificate identity and source commit before trusting it, downloads the exact `pi-<target>.zip` for `piConfig.releaseTarget`, verifies the ZIP digest from the authenticated manifest, extracts the single entry, verifies the executable digest, and activates it. Missing, forged, or wrong-identity proof rejects that source without disabling verification, including under `--force`. An xz-dev source checkout remains user-managed.
- Self-update is lock-free: the running executable moves itself to a strict-version backup `pi-<old-version>` (`pi-<old-version>.exe` on Windows) next to the install path, downloads, verifies and extracts the new executable, then atomically replaces the public path. `pi update --clean` removes only `pi-<version>` backups whose names are exact semver matches; unrelated sibling files and the running executable are left untouched.
- Provenance verification requires no GitHub login. `attestation-subjects.jsonl` is prepared as a pre-sign filename list and replaced by the verified signed Sigstore bundle after attestation; it is the shipped Release proof asset and is not itself an attestation subject. The signed bundle is verified against every subject twice: once in `attest-release-candidate` (including an empty-`GH_CONFIG_DIR` run) and again in `publish-release` against the exact certificate identity `https://github.com/xz-dev/pi/.github/workflows/publish-github-release.yml@refs/heads/main`, `--source-ref refs/heads/main`, `--source-digest $GITHUB_SHA`, and `--deny-self-hosted-runners`, before the draft is published. First installs follow the README flow: an independently trusted `gh` binary verifies the archive against the shipped bundle, exact release, and full source commit before extraction or execution. Sigstore TUF network access during verification is permitted and documented; fully offline installation is not claimed. Bundled trusted-root coverage is finite: a Sigstore public-good root rotation requires a client update through a separately trusted installation path, and mirrors can replay or withhold authentic releases — signatures prove origin and integrity, not freshness.
- Do not publish this fork to npm, GitHub Packages, tags outside `xz-v*`, or a second Release plane. `.github/workflows/build-binaries.yml` is persistently removed from generated `main`; the `ci` overlay and generated-main verification continue removing it if upstream ever reintroduces it.

## Patch retirement

Temporary retirement removes a patch from sync fetch/merge/test integration and enabled README features while retaining its source branch for re-evaluation. Do not archive or delete the source ref.

Permanent retirement requires verified replacement evidence, removal from configured order and README, a validated rebuilt `main`, archival to `archive/<patch-name>`, then deletion of the original `patch/<patch-name>` ref.
